# TC-MOB-207 打开会话首帧直接落在最新位置

**要验的缺陷**：在会话列表点开一条**已经看过**的会话时，新那一屏的第一帧先画在被恢复窗口的
**开头**（视口 offset=0），约 120ms 后才被宿主的异步钉底送到尾部。观感是"打开先闪一下开头，
再跳到结尾"；会话越长跳得越远。首次打开（无缓存）不受影响，二次进入必现。

**为什么会这样**：`TranscriptListHost.apply(.setRows)` 在 diffable 数据源**还没落快照**时
就调用 `satisfyBottomIntent()`；那一刻 `numberOfItems == 0`，`bottomTarget()` 只能算出 0，
于是先钉在内容顶端。快照落地后系统画出第一帧（开头），下一拍异步钉底才把它送到尾部。

**为什么截图抓不到**：这一跳在 100–150ms 内完成，引擎拍延迟截图前会先等画面静止；
`simctl` 又拍不到 XCUITest 驱动的 App。所以判据落在宿主自己报的探针行
`open.nonbottom`（第一次把行布局出来那一拍量距底距离，>1pt 就写一行）。
根因与修复见 `handbook/requirements/details/sessions.md` 的 SR-02.17。

**数据**：`会话` 钉住的是一条已完成的真实长会话，只读：只点行进入/返回，不输入、不点内容。
它必须长到超过一屏，否则"首帧在开头"与"在结尾"是同一屏，量不出来。夹具失效时按 `备注` 换一条。

## 步骤

1. 打开会话列表，带 `-DSHViewportProbe`。
2. 滚动到该会话行并点开（首次进入），等 3 秒。截图 01。
3. 返回会话列表。
4. 再点同一行（二次进入，命中内存缓存），等 3 秒。这一步就是缺陷现场。
5. 停在转写页。截图 02。
