# 测试规则

这份文件是判定的依据。**只有用户能改**；改了就升版本号，报告里写明按哪一版判的。
测试者（AI）不得为了让某条用例变绿而修改这份文件或用例本身。

当前版本：**v3**（2026-09-16）——v2 到 v3：用例必须声明「通过判据」（判据先写死，
判定不许换标准）；报告新增「结论建议」（合入／有条件合入／不合入）与指标概览、
测试环境、耗时；v1 到 v2：报告规范升为契约（`REPORT-CONTRACT.md`），判定必须带依据，
逐步记录必须写观察到的事实与证据，`report` 改为 lint 闸门。

## 一、谁做什么

| 角色 | 负责 |
|---|---|
| 用户 | 定规则（本文件）、定用例（`cases/fixed/`）、最终审视判定 |
| 测试者（AI） | 决定跑哪些用例、写 `cases/current/` 的临时用例、执行、看截图、出报告、给判定 |
| 测试者不得 | 修改固定用例与规则；把失败的用例改成通过；在没看过截图的情况下判通过；把没跑到的步骤写成通过 |

跑测试的主动权在测试者：`prepare` / `run` / `shot` / `scaffold` / `report` 五个动作按需调用，
脚本只承担机器那部分（驱动、截图、像素核对、lint、排版），不决定测什么、也不决定结论。

**通用规范在全局 skill 里**，本文件只写本项目的特殊约定：
`agent-testing`（测试标准：用例怎么写、证据要到什么程度、四态怎么判、报告必须有什么）
与 `ios-sim-testing`（这台机器上怎么驱动仿真器）。两者与 `test/REPORT-CONTRACT.md`
冲突时，以 `REPORT-CONTRACT.md` 为准——它是被 `report.py` 强制执行的那一份。

## 二、用例从哪来

- **固定用例** `test/cases/fixed/`：用户决定，只增不改。要改用例必须用户点头，
  并在提交信息里写明原因。
- **当前用例** `test/cases/current/`：每做一件事（改 bug、加功能）先写一条，
  改名或删除都随这件事结束。**没有用例的改动不算完成。**
- 每个用例两个文件：`序号-中文标题.md` 是纯自然语言的用例（给人和评审看），
  同名 `.steps` 是逐行对应的执行指令（机器看）。两份的第 N 步必须一一对应。
- 用例 front matter 必须有 **`通过判据:`**——这条用例「什么算通过」先写死
  （例：12 步结论全为通过；6 张截图无截断/重叠/错误色；像素核对全部通过；无未验证步骤）。
  报告第 2 节会原样列出，判定必须按它给；没声明判据的用例，`report` 判「报告不完整」。

## 三、一次运行的判定

一条用例的判定由四部分组成，缺任何一项都不算完成：

1. **引擎判定**——步骤断言是否通过（`report.html` 顶部指标概览）。
   任一步失败即 `FAIL`；重复执行会覆盖同一步的上一次结果，报告里只留最后一次。
2. **像素核对**——可算的那部分：有没有文字、有没有出现本项目的错误色、
   有没有混进不该有的琥珀／橙色。这些是辅助证据，不单独决定通过。
3. **视觉核对**——测试者逐张看标注截图，判断文字、图形、线条、颜色、版式。
   断言绿了但界面空白、错位、文字被截断，仍判失败。
4. **报告完整性**——`report` 的 lint 通过：用例声明了通过判据、执行前声明四项齐全、
   每步有实际现象与结论、`实际` 不复述期望、证据可核对、产品类缺陷五行齐全。
   任一项缺失，报告判为 **报告不完整**，不算判定。

每步的记录形如：操作 → 期望效果 → 实际现象 → 判定依据 → 本步结论。
`实际现象` 写观察到的事实（条数、位置、耗时、报错原文），**不许复述期望**；
`判定依据` 写凭什么这么判（截图编号、事件流 id、实测数字）。

最终判定取四态之一，写在报告的「判定」一节，并附一句话结论与判定依据。
报告还会按事实推出 **结论建议**（合入／有条件合入／不合入），口径：
报告不完整或未验证 → 不合入；可疑 → 有条件合入；失败 → 不合入；其余 → 合入。
建议由脚本算，不由测试者写——测试者要影响它，只能改判定与依据。

| 判定 | 什么时候用 |
|---|---|
| **通过** | 该测的都测到了，没发现问题 |
| **可疑** | 有问题但不确定是不是缺陷，或有一部分没测到；需要用户定夺 |
| **失败** | 明确不符合预期 |
| **未验证** | 环境不具备等原因没测成，不算通过也不算出问题 |

最终由用户审视确认。

## 四、失败怎么记

每条失败必须归到下面三类之一，写明「影响 / 复现 / 证据」，写进 `report.html` 的
「发现」一节：

| 类别 | 含义 | 处理 |
|---|---|---|
| `产品` | App 的行为或显示与用例预期不符 | 记为缺陷：最小复现 + 证据截图 + 影响面 + 处理建议；是否修由用户决定 |
| `用例` | 用例本身写错了（元素不存在、预期不合理） | **只报告，不改固定用例**，等用户决定 |
| `环境` | DSH 没在跑、仿真器状态脏、中转不通 | 重试一次；仍失败记「未验证」，不算通过 |

「未验证」不等于通过。跳过也要写原因。

**偶发问题**（时好时坏）单独处理：同一用例连跑三次，把三次的结论与复现次数都写进报告，
否则只能记「可疑」——一次没复现不等于修好了。
**改动类用例**要先在旧代码上跑出失败（red-check），再在新代码上跑出通过；只贴通过那次
说明不了这个用例抓得住缺陷。

## 五、证据与报告

- 每次运行一个目录 `test/runs/<年月日-时分>/`：
  `report.html`（给人看的报告）、`review.md`（步骤评审，你可改）、`shots/` 原图、
  `annotated/` 标注图、`summary.json`（机器可读结果，含 `lint` 与 `previousIssues`）、
  `detail/`（xcresult、事件流、用例翻译、像素明细）。
- 每个要核对的步骤至少一张图，命名 `序号-步骤-名字.png`，序号即报告里的顺序。
- 标注图带用例号、步骤、核对说明和判定，可单独发给人看。
- **报告的章节、`review.md` 的写法、lint 规则见 `test/REPORT-CONTRACT.md`**，
  那是唯一权威；`report` 会按它校验，不合格不出正式判定。
- `test/runs/` 不进 git：它是本机数据，任何时候可以用同样的用例重跑出来。

## 六、不许碰的东西

- `~/.dsh/` 下的真实会话与凭据：用例只读地打开，绝不写入。
- 需要造数据时用临时会话，跑完删掉；单测把 `DSH_HOME` 指向临时目录。
- 中转 agent 凭据从 `~/.dsh/mobile-link/agent.json` 读，绝不写进仓库。
- 破坏性手势（左划归档、长按菜单）只允许作用在临时会话上；目标元素找不到时
  **必须判失败，不许按坐标兜底**。

## 七、耗时约定

- 一轮典型回归（3–6 步的用例）控制在 1–2 分钟。
- 单条行为用例超过 2 分钟视为需要拆分。
- 能用启动参数直达的页面，不要用点按一步步走过去。
