# 测试报告契约

这份文件规定一份报告必须具备什么。**测试者（AI）写、`report.py` 校验并排版、
用户审视**。规范的通用部分（测试哲学、流程纪律、判定口径）在全局 skill
`agent-testing` 里，这里只写这份报告本身。

报告可能被单独转发给人看（手机、邮件、issue），所以它必须**自洽**：
看图的人不在现场，看不到仿真器、会话、构建，报告里没有的等于没发生。

## 一、报告章节

顺序固定，缺一节即 lint 报错（确实不适用的节写「无」，不要删节）。

| 节 | 内容 | 数据来源 |
|---|---|---|
| 报告头 | 运行号、用例与版本、代码版本、App 版本、host／仿真器、用例文件 | `summary.json`，脚本填 |
| 1 判定 | 四态 + 一句话结论 + **判定依据** + **结论建议**（合入／有条件合入／不合入）+ **指标概览**（用例通过、引擎断言、像素核对、未验证、截图覆盖、耗时） | `--verdict`/`--note`、`review.md`，指标由脚本算 |
| 2 通过判据 | 用例声明的「什么算通过」，原样列出；没声明就按契约默认判据审 | 用例 front matter 的 `通过判据:` |
| 3 执行前声明 | 被测构建、数据来源、覆盖边界、基线状态 + **测试环境**表（代码版本／App 版本+build／仿真器／设备型号／系统版本／Xcode／测试机／host／执行时间／耗时） | `review.md` 的 `## 声明` + `summary.json` 的 `environment` |
| 4 发现 | 每条问题的类别、影响、复现、证据 | `review.md` 的 `## 发现` 节 + 引擎失败项 + 像素未过项 |
| 5 逐屏核对 | 每步：操作 → 期望效果 → 实际现象 → 判定依据 → 本步结论，附图 | `plan.json` + `summary.json` + `review.md` 的 `## rN` |
| 6 未覆盖与风险 | 已覆盖／未覆盖的计数 + 未验证／可疑的路径与风险 | 脚本按四态统计 + `review.md` 的声明 |
| 7 上轮问题回归 | 上轮问题这次的结论；脚本另列出历史运行里未解决的问题 | `review.md` 的 `## 回归` + `summary.json` 的 `history` |
| 8 产物 | `shots/`、`annotated/`、`detail/`、`summary.json` | 脚本填 |

**结论建议**由脚本按事实推出，顺序：报告不完整 → 不合入；未验证/ERROR → 不合入；
可疑 → 有条件合入；失败/FAIL → 不合入；其余 → 合入。它写在报告里、也写进
`summary.json` 的 `posture`（`GO`/`CONDITIONAL`/`NO-GO`），所以「能不能合入」不需要
读者自己从四态里猜。

## 二、`review.md` 的格式

测试者逐字写这个文件；`report` 只读它，不改它。改完重跑 `report` 即可，不用重跑用例。

### 声明（执行前写，跑之前就该想清楚）

```markdown
## 声明

构建: 3a81353（Debug，仿真器 <UDID>）／ App 1.0
数据: 「临时目录 /tmp/dsh-uitest-scratch」下的会话，跑完已删；真实会话只读打开
边界: 只测首屏可见内容（断言看不到屏幕外），屏幕外仅留截图；系统相册/文件选择器不测
基线: 上轮遗留「设置页在直连下不显示已配对设备」，与本轮无关
```

四项缺一即 lint 报错。`边界` 要写**没测什么、为什么**，不是重复测了什么。

### 每一步

```markdown
## r3

操作: 打开页面 transcript（取历史最丰富的会话）
期望: 转写渲染出真实历史
实际: 47 行消息渲染完整；中文与代码块字体正确；最后一行是「已完成」分隔线
依据: 截图 03 与 detail 事件流 s03 一致；像素核对无错误色；无截断与重叠
结论: 通过
异常: 无
```

- `实际` 写**观察到的具体事实**（数字、计数、位置、耗时、报错原文），
  禁止复述 `期望`、禁止只写「正常」。lint 会算两者的重合度。
- `依据` 写「凭什么这么判」——引用截图编号、事件流 id、像素核对结果、实测数字。
- `异常` 只在有问题时写，格式：`级别|描述|复现`，一条一行：
  `异常: 产品|第 3 行消息重复 3 份|重进会话 3/3 次`
- `结论` 取四态：`通过` / `可疑` / `失败` / `未验证`。
- 一段可覆盖连续多步（`## r1–r16`），但被覆盖的每一步都要有结论；
  `实际`/`依据` 只写一次，lint 接受。

### 发现（类别取 `产品` / `用例` / `环境`）

```markdown
## 发现

产品: 重进会话后同一条回答重复渲染（3 份）
影响: 用户会以为模型回答了多次；症状在长会话里更明显
复现: 会话 A → 返回列表 → 再进入，3/3 次
证据: 截图 04；detail/events.json 的 s17
处理建议: 转写行身份按 event.seq 派生，而不是按到达顺序追加
```

`产品` 类必须写全五行。`用例` 类只报告不改用例，写明「等用户决定」。
`环境` 类写明已重试几次。

### 回归（上轮有未解决问题时必写）

```markdown
## 回归

上轮: TC-UI-01 失败——设置页滑到底部时「关于」被截断
本轮: 通过（截图 09 完整显示）；同一屏其余分组无回归
```

## 三、lint 规则（`report.py` 自动执行）

阻断级（报错，不出报告）：

| 代号 | 规则 |
|---|---|
| `step-missing` | 用例有 N 步，`review.md` 里缺某步的结论 |
| `missing-declaration` | `## 声明` 缺 `构建`／`数据`／`边界`／`基线` 任一项 |
| `verdict-invalid` | 某步结论不是四态之一 |
| `observed-empty` | `实际` 为空 |
| `observed-parrots` | `实际` 与 `期望`／用例原文重合度过高（Jaccard > 0.7，或期望是实际的子串且实际不足 1.3 倍长） |
| `evidence-weak` | `实际` 与 `依据` 都没有任何具体证据（数字、计数、耗时、报错原文、截图编号） |
| `finding-incomplete` | `产品` 类发现缺 `影响`／`复现`／`证据` |
| `no-judgement-basis` | 判定为通过或失败，但 `判定依据` 为空 |
| `no-criteria` | 用例 front matter 没有 `通过判据:`（判据没声明就等于可以随时改标准） |
| `artifact-missing` | 报告引用的截图文件不存在 |

提醒级（出报告，但列进「需要留意」）：

| 代号 | 规则 |
|---|---|
| `uncovered` | 有步骤判定为未验证／可疑，报告会列进第 6 节 |
| `shot-missing-for-step` | 结论要求目视核对（含「截图留证」等字样）但没有截图 |
| `regression-absent` | 上一轮有未解决问题，本轮没有 `## 回归` |
| `evidence-thin` | 有可核对的东西，但整段没有数字 |
| `no-criteria` | 判据缺失但该运行早于本规则生效时间（历史运行只提醒不拦） |

## 四、lint 自己也要被测

lint 是这份契约唯一的执行者，规则悄悄失效就等于契约作废。所以每条规则都有一个
反例测试：`test/tools/test_report.py` 构造一份「只违反这一条」的评审记录，
断言它确实被拦下。

```bash
test/.venv/bin/python test/tools/test_report.py    # 全部通过才算 lint 可用
```

**改 `report.py` 的 lint 或改本文件第三节的规则表时，必须同时改这个测试**；
只加规则不加反例，视同没加。

## 五、给脚本作者的两条约束

1. **报告只引用 `annotated/` 与 `shots/` 里的文件**，不内嵌 data URI——
   单行几十万字符会让手机端阅读器卡死（判据-7）。
2. **判定不写进渲染层**：`--verdict` 与 lint 结果都写回 `summary.json`
   （`judgement`、`judgementNote`、`posture`、`facts`、`criteriaDeclared`、`lint`、`history`），
   使机器可读的结论与报告一致。
3. **环境与耗时由运行器采集，不在渲染时现查**：`summary.json` 的 `environment`
   （仿真器／设备型号／系统版本／Xcode／测试机）与 `durationSeconds` 由 `run.mjs` 在跑的时候写入——
   报告可能几天后才生成，那时机器状态已经变了。缺字段时报告显示 `?`，不许因此失败。
