# 系统化排查

先根因，后修复。第一阶段没完成，不得提出任何修法；未复现就动手，视为违规。

改写自 obra/superpowers 的 `systematic-debugging`（MIT），按本仓库证据口径调整。

## 第一阶段：复现与取证

1. 读完整报错与栈，不跳读；记下文件、行号、退出码。
2. 稳定复现，写清最小步骤。不能稳定复现时继续取证，不猜。
3. 查最近改动：`git log --oneline -10`、`git diff`、依赖与配置变化。
4. 多组件链路（iPhone → relay → connector → dsh）按边界打点：每段记录输入、输出、环境变量是否送达，先定位断在哪一段，再深入该段。
5. 证据落盘：`maintainers/debug-<slug>/` 或 `.lanes/runs/<run-id>/`，会话里只引用路径。

## 第二阶段：模式对比

- 找同仓库里能正常工作的同类实现，逐行对比差异。
- 引用外部实现时读完整，不凭印象套用。
- 差异列全，包括看起来无关的配置与版本。

## 第三阶段：单一假设

- 用一句话写出假设：「我认为 X 是根因，因为 Y」。
- 只改一个变量做最小验证；一次改多处等于没验证。
- 不成立就换新假设，不在旧修法上叠加。
- 不确定就明说「我不知道 X」，并补充取证。

## 第四阶段：实现

1. 先写能失败的用例（纯逻辑模块；iOS 视觉问题用仿真器截图复现，见 `ios-sim-testing`）。
2. 只改根因，一处修复，不夹带重构与「顺便优化」。
3. 验证按 `verification-before-completion` 执行；提交前过 `.githooks/pre-commit`（靶向测试 ≤30s + Diff 审查 ≤5s）。

## 三次失败即停

同一问题修复三次仍不收敛，停止尝试第四次，回到 `team-architect` 质疑架构：是否共享状态、职责归属或通路设计本身有问题。写明已试过的修法与证据，交回设计阶段。

## 禁止的手法

- 为单个症状加 `if/elif` 特例、开关、缓存或第二条通路。
- 用重试、加长超时、多等一会掩盖未知终态。
- 用「加日志再看看」代替定位（日志只用于取证，取证完要有结论）。
- 把未复现的问题直接改成「应该好了」。

## 交接内容

根因、职责归属、迁移与回滚路径、被删除的旧行为，写进改动记录；测试工程师据此设计用例，架构师据此评审。
